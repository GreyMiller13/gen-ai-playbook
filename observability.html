Наблюдаемость LLM-решений

observability — возможность по телеметрии отвечать на вопросы о поведении системы, которые не были известны заранее. Для LLM-приложений это прежде всего tracing: дерево вызовов trace / span, где каждый шаг агента — модель, retrieval, инструмент — виден с аргументами, токенами, латентностью и стоимостью.

Что это и зачем аналитику

Классического APM (логи, метрики HTTP, алерты на 5xx) для LLM-приложения мало по трём причинам:

  • недетерминизм: одинаковый вход даёт разные выходы; ответ может быть «успешным» по HTTP и бесполезным или вредным по смыслу — деградация не выглядит ошибкой;
  • качество — метрика: faithfulness, полнота, доля эскалаций не выводятся из кодов ответа, их надо собирать отдельно (телеметрия + обратная связь + выборочные проверки);
  • дрейф: поведение меняется без вашего релиза — провайдер обновляет модель, меняется распределение пользовательских запросов, «тихие» регрессии накапливаются.

Роль аналитика: определить, что считается телеметрией (какие события, спаны, метрики), что логируется с контентом, а что без, какие пороги триггерят алерты и как телеметрия замыкается в цикл улучшений (трейсы → датасеты → evals → релиз промпта).

Как устроено: трейсинг

Запроспользовательская сессия
→
Traceroot span агента
→
SpansLLM / retrieval / tool
→
ЭкспортOpenTelemetry-коллектор
→
Платформатрейсы, метрики, алерты

Модель данных: trace — полный путь одного запроса через приложение; span — одна операция с именем, таймингами (start / end), атрибутами, событиями и статусом. Спаны вложены: span вызова LLM лежит внутри span-а шага агента, а все вместе связаны общим trace_id. Сессия пользователя объединяет несколько трейсов (диалог).

Что должно попадать в спан LLM-вызова
  • имя модели и параметры вызова (temperature, max_tokens);
  • промпт и ответ — с учётом политики PII (см. ниже), опционально;
  • вызовы инструментов: имя, аргументы, результат, ошибки;
  • счётчики токенов: input / output (и кэшированные, если провайдер отдаёт);
  • латентность спана и статус (ok / error + тип ошибки);
  • стоимость — вычисленная по тарифам, если платформа не считает сама.

Правило полноты: по одному трейсу должно быть возможно реконструировать, почему агент ответил именно так — какой retrieval дал какие документы, какая модель с какими параметрами генерировала, какой guardrail что отклонил.

OpenTelemetry и GenAI-конвенции

OpenTelemetry (OTel) — открытый стандарт телеметрии; трейсинг — один из его сигналов. Специфичные для генеративного AI конвенции — GenAI semantic conventions — развиваются в отдельном репозитории проекта (open-telemetry/semantic-conventions-genai) и на момент проверки находятся в статусе Development, то есть имена атрибутов могут меняться.

Что определено в конвенциях: спаны LLM-вызова (client inference), эмбеддингов, выполнения инструментов, retrieval, вызова агентов; события и метрики, включая токены. Ключевые атрибуты спана LLM-вызова: gen_ai.operation.name и gen_ai.provider.name (обязательные), gen_ai.request.model, gen_ai.usage.input_tokens / gen_ai.usage.output_tokens, gen_ai.response.finish_reasons.

PII в конвенциях

Захват содержимого промптов и ответов (gen_ai.input.messages, gen_ai.output.messages, системные инструкции, определения инструментов) — opt-in: конвенции прямо предупреждают, что эти атрибуты «likely to contain sensitive information including user/PII data». Предусмотрена альтернатива — ссылки *_ref на внешнее защищённое хранилище контента.

Платформы трейсинга LLM (сравнение в одном абзаце): LangSmith от LangChain — коммерческая платформа трейсинга, мониторинга и отладки LLM-приложений и агентов с оценками и управлением промптами, есть облачный и self-hosted варианты развёртывания. Langfuse — open-source платформа для инженерии AI-приложений: трейсинг с сессиями, оценки (LLM-as-judge, датасеты, эксперименты), управление промптами, метрики стоимости и латентности; допускает self-hosting и облако. Arize Phoenix — open-source платформа AI-observability и оценок от Arize, трейсинг построен на OpenTelemetry, доступна как self-hosted, так и управляемая версия.

Логирование

Лог — дискретное событие, трейс — дерево вызовов с контекстом; для отладки агентов нужен трейс, логи дополняют его. Какие события логировать обязательно:

  • решения guardrails: пропуск / отказ / эскалация и причина;
  • решения роутинга: какая модель выбрана и почему (если есть router);
  • вызовы инструментов: имя, аргументы (с маскированием), результат, ошибки, таймауты;
  • ошибки API провайдера и ретраи;
  • исходящий фидбек пользователя (thumbs, CSAT) с привязкой к trace_id.
Антипаттерн

Писать полные промпты и ответы в общий лог «по умолчанию». Телеметрия становится самым широким каналом утечки PII: доступ к трейсам обычно шире, чем к самим данным. Контент — opt-in, с маскированием и ограничением доступа.

Онлайн-метрики качества

Технические метрики (латентность, ошибки) необходимы, но недостаточны; качество измеряется поведенческими метриками:

Доля эскалаций (escalation rate) эскалации / все обращения за период Сколько диалогов передано человеку. Рост — деградация качества или пробелы в базе знаний; ноль — подозрение, что агент не отдаёт сложное вообще.
Thumbs up / down негативные оценки / все оценки ответа Прямая обратная связь пользователя по конкретному ответу; привязывается к trace_id. Учитывайте смещение выборки: чаще оценивают недовольные.
CSAT средняя оценка удовлетворённости по сессии (шкала, например 1–5) Классический опрос в конце сессии; грубее thumbs, но сопоставим с другими каналами поддержки.
Доля отказов (refusal rate) ответы-отказы / все ответы Отказ по guardrail — не всегда плохо; важно разбивать по причинам (запрещённая тема / нет данных / подозрение на инъекцию).
Повторные вопросы (re-ask rate) сессии с повторной формулировкой того же вопроса / все сессии Прокси непонятных или неполных ответов: пользователь переспрашивает, не получив нужного.

Мониторинг деградаций и алертинг

Источники «тихих» регрессий и что с ними делать:

  • смена версий моделей провайдером: закрепляйте снапшоты, где это возможно, и фиксируйте фактическую версию модели в каждом трейсе (атрибут вида gen_ai.response.model); алерт на смену значения — деградация без вашего релиза;
  • дрейф запросов: после релиза продукта или сезонности меняются темы и длина промптов — смотрите метрики по сегментам, а не только глобально;
  • тихие регрессии промпта: перед релизом промпта — прогон по golden dataset; после релиза — сравнение метрик качества с базовой линией.
Трейсы как источник golden dataset
  • неудачные трейсы (негативный фидбек, эскалации, провалы faithfulness) — кандидаты в golden dataset: новый кейс для регрессионного прогона;
  • перед добавлением — очистка PII и фиксация ожидаемого правильного ответа;
  • такой цикл (прод → датасет → evals → прод) — главный механизм, ради которого вообще нужна телеметрия контента.

Пороги алертов (от чего зависит здоровье системы):

  • p95 латентности ответа и p95 TTFT — отдельно;
  • error rate вызовов провайдера и доля ретраев;
  • доля эскалаций и негативного фидбека — рост к базовой линии, не абсолют;
  • стоимость на тикет / сессию / день — выход за бюджет;
  • смена значения атрибута версии модели в трейсах.

Пример: структура трейса агента

Иллюстративная структура (имена атрибутов — по мотивам GenAI-конвенций OTel, статус Development; формат упрощён):

trace 7f3a...
├─ session_id: "sess-1024", user_ref: "u-hash"        // без PII
├─ span agent (root)
│  ├─ span retrieval "vector_search"
│  │   ├─ query: "ошибка интеграции 1c-toir", top_k: 5
│  │   └─ doc_ids: [a1, b7, c2], latency_ms: 180
│  ├─ span gen_ai.client.inference   // вызов LLM №1: выбор действия
│  │   ├─ gen_ai.operation.name: "chat"
│  │   ├─ gen_ai.request.model: "model-x"
│  │   ├─ gen_ai.usage.input_tokens: 2150
│  │   ├─ gen_ai.usage.output_tokens: 90
│  │   └─ latency_ms: 640
│  ├─ span execute_tool "ticket_lookup"
│  │   ├─ args: {ticket: "TS-4112"}, status: ok
│  │   └─ latency_ms: 220
│  └─ span gen_ai.client.inference   // вызов LLM №2: финальный ответ
│      ├─ gen_ai.usage.input_tokens: 3800
│      ├─ gen_ai.usage.output_tokens: 410
│      └─ gen_ai.response.finish_reasons: ["stop"]
├─ span output_guard: citations_ok: true, latency_ms: 90
└─ итоги: tokens_in 5950 / tokens_out 500,
   cost_est: ..., latency_ms: 4200, feedback: thumbs_up

Такой трейс отвечает на вопросы разбора инцидента: какие документы найдены, что выбрала модель, что вернул инструмент, сколько стоил и длился каждый шаг. Числа иллюстративные.

Антипаттерны

Антипаттерн

Только технические метрики: HTTP 200, средняя латентность, uptime. Всё зелёное — ответы при этом бесполезны; качество должно быть метрикой первого класса.

Антипаттерн

Средние без перцентилей. Средняя латентность прячет хвост из медленных сессий (ретраи, длинные документы); SLA и алерты строятся на p95.

Антипаттерн

Трейсы собираются «про запас», их никто не разбирает. Без процесса разбора инцидентов и переноса кейсов в golden dataset телеметрия — только расход на хранение.

Антипаттерн

Алерты на всё подряд либо ни на что. Первое приучает игнорировать (alert fatigue), второе пропускает тихие регрессии на недели — особенно после смены модели провайдером.

Антипаттерн

Контент логируется без политики: нет решения «что можно хранить, сколько, кто видит». Утечка через телеметрию — штатный сценарий инцидента, а не экзотика.
