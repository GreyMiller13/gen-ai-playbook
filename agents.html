AI-агенты и оркестрация

AI agent — это LLM, работающая в цикле: модель сама планирует шаги, выбирает инструменты, получает результаты и повторяет итерации, пока не выполнит задачу. Раздел — про устройство этого цикла, подключение инструментов и выбор схемы оркестрации.

Содержание страницы

Что это и зачем аналитику

В инженерном определении Anthropic агент — система, в которой LLM «динамически направляет собственные процессы и использование инструментов», сохраняя управление ходом выполнения задачи. Рабочая формула: модель + инструменты + память + критерий остановки. Модель — принимает решения; инструменты (tools) — действия и источники данных; память — контекст диалога и внешние хранилища; критерий остановки — условие завершения (задача решена, лимит шагов, эскалация человеку).

Отличать агента стоит от двух соседей. chatbot — диалог без инструментов: модель отвечает в один-два шага и не меняет внешний мир. workflow — процесс, где шаги с LLM соединены заранее написанным кодом: порядок вызовов фиксирован, модель заполняет только содержимое шагов. У агента порядок шагов выбирает сама модель на каждом витке цикла.

КритерийЧат-ботWorkflowАгент
Кто задаёт порядок шагов Диалог, один шаг за реплику Жёстко задан кодом Модель планирует сама, шаг за шагом
Инструменты Нет или простая вставка данных Фиксированный набор на каждом шаге Модель выбирает из реестра доступных tools
Предсказуемость Высокая по ходу, низкая по содержанию Высокая: путь известен заранее Ниже: путь зависит от модели и данных
Стоимость и латентность Минимальные Средние и предсказуемые Выше и варьируются: много вызовов модели
Когда уместен FAQ, типовые консультации Стабильный процесс с известными шагами Открытая задача с непредсказуемым числом шагов
Заметка

«Агент ради агента». Если задача решается фиксированным пайплайном или одним вызовом модели с retrieval — агент не нужен: стоимость, латентность и непредсказуемость растут, а выгоды нет. Anthropic рекомендует брать самое простое решение и усложнять его только когда это измеримо улучшает результат.

Зачем это аналитику: спроектировать агента — значит описать требования не к экранам, а к границам системы. В спецификацию агента входят: реестр инструментов и их схемы, границы полномочий, лимиты (шаги, токены, время), точки подтверждения человеком и правила эскалации. Это работа аналитика, а не только разработчика.

Как устроено

Цикл агента

Ядро агента — повторяющийся цикл «модель → выбор инструмента → результат → модель» (agent loop):

LLMплан шага: ответить или вызвать инструмент
→
Tool callимя инструмента + аргументы в JSON
→
Исполнениеприложение или внешний сервис
→
Результатдобавляется в контекст диалога
→
LLMследующая итерация или финальный ответ

Цикл повторяется, пока модель не решит, что задача выполнена, либо пока не сработает критерий остановки: лимит итераций, бюджет токенов, таймаут, запрос подтверждения человеком (human-in-the-loop) или эскалация.

Tool calling: механика

tool calling (синоним — function calling) — протокол взаимодействия модели с кодом приложения. Схема из пяти шагов (по документации OpenAI):

  1. Приложение отправляет модели запрос и список доступных инструментов: имя, описание, параметры в виде JSON Schema.
  2. Модель решает, нужен ли инструмент, и возвращает tool call — имя функции и аргументы в JSON. Исполнять её модель не может: это делает приложение.
  3. Приложение исполняет вызов своим кодом: запрос к API, поиск в базе, файловая операция.
  4. Результат отправляется обратно в модель и добавляется в контекст диалога.
  5. Модель либо выдаёт финальный ответ, либо делает следующий вызов (возможно, несколько параллельных).

Схемы инструментов попадают в системную часть контекста и тарифицируются как входные токены, поэтому «зоопарк» инструментов удорожает каждый запрос. OpenAI рекомендует ориентироваться на небольшое число функций (в её гайде — порядка двух десятков как мягкий ориентир) и оценивать точность выбора на своих данных. Режим strict mode гарантирует, что аргументы вызова соответствуют JSON Schema.

Model Context Protocol

Model Context Protocol (MCP) — открытый протокол, стандартизующий подключение внешнего контекста и действий к AI-приложению: единый контракт «инструменты + данные» вместо индивидуальных интеграций под каждую пару «приложение — сервис». Архитектура клиент-серверная: host (AI-приложение) создаёт по одному MCP client на каждый MCP server; обмен — через JSON-RPC 2.0. Сервер может выставлять три примитива:

ПримитивЧто даётПример
tools Исполняемые функции: действия и запросы запрос к БД, создание тикета, файловая операция
resources Данные-контекст для чтения моделью содержимое файла, запись из справочника
prompts Переиспользуемые шаблоны взаимодействий заготовка системного промпта с few-shot примерами

Транспорта два: stdio — локальный запуск сервера как процесса на той же машине (без сетевых накладных расходов) и Streamable HTTP — удалённое подключение по HTTP с потоковой передачей и стандартной авторизацией. Аналитику MCP даёт готовый единый контракт: вместо спецификации «модель ↔ каждая система» достаточно описать MCP-сервер каждой системы один раз — его подключит и LLM-приложение, и IDE, и агентский рантайм.

Память агента

  • Короткая память — контекст текущего диалога или задачи: системный промпт, история сообщений, результаты инструментов. Ограничена context window и растёт с каждым шагом цикла.
  • Долгосрочная память — внешнее хранилище (векторная БД, таблица фактов, файлы), которое приложение подгружает в контекст по мере надобности: предпочтения пользователя, история прошлых обращений, база знаний.
  • Суммаризация истории — сжатие старых сообщений в краткое резюме (summarization), чтобы уложиться в окно, не потеряв сути диалога. В LangGraph это часть встроенных механизмов памяти и персистентности.

Паттерны оркестрации

orchestration — организация вызовов модели, инструментов и агентов в единый процесс. Чем больше свободы у модели, тем выше гибкость и тем ниже предсказуемость:

ПаттернКак работаетКогда уместенТрейд-оффы
router (маршрутизация) Классификатор раскладывает вход по веткам; в ветке — промпт или workflow Типы обращений известны заранее (вопрос / жалоба / инцидент) Дешёво и предсказуемо; ошибки классификации нужно обрабатывать
Один агент с инструментами Единственный agent loop; модель сама выбирает tools из реестра Задача открытая, но одна область и умеренный набор инструментов Простая отладка; при росте числа tools точность выбора падает
supervisor + рабочие агенты Координатор декомпозирует задачу, раздаёт подзадачи рабочим агентам, собирает результат Задача разбивается на разнородные подзадачи с разными инструментами Масштабируется по возможностям; дороже, сложнее трассировка
multi-agent система Несколько агентов с ролями взаимодействуют напрямую или через общего координатора Параллельная работа над независимыми частями, «командная» обработка Максимальная гибкость; умножение стоимости и ошибок, нужен аудит коммуникаций

Промежуточные варианты из статьи Anthropic: prompt chaining (цепочка шагов с проверками-шлюзами), параллелизация (независимые подзадачи или несколько прогонов с «голосованием»), orchestrator-workers (супервайзер-схема, где подзадачи не заданы заранее) и evaluator-optimizer (один вызов генерирует, второй критикует и правит).

Human-in-the-loop и эскалация

Автономность агента ограничивают точками контроля:

  • Подтверждение перед действием — irreversible-операции (платёж, удаление, рассылка, изменение общих данных) агент предлагает, человек подтверждает.
  • escalation — передача задачи человеку или следующей линии при исчерпании возможностей агента: нет данных в базе знаний, низкая уверенность, превышен лимит шагов, запрос вне полномочий.
  • Правило эскалации фиксируется в спецификации явно: условия, маршрут (тикет, чат, дежурный), передаваемый контекст (история шагов, найденные факты).

Фреймворки одним абзацем

LangChain — фреймворк приложений на LLM: единый интерфейс к провайдерам моделей и надстройка create_agent для быстрого агента с инструментами. LangGraph — низкоуровневый фреймворк и рантайм от той же команды для длительных stateful-агентов: процесс задаётся графом состояния, встроены персистентность, память, streaming и human-in-the-loop; LangChain сам построен на его фундаменте. CrewAI — фреймворк мультиагентных систем: «экипажи» агентов с ролями, целями и инструментами плюс событийные Flows для управления ходом процесса. LlamaIndex — «data framework» для LLM-приложений с акцентом на данные: коннекторы-приёмники, индексы и движки retrieval/query для RAG и агентных сценариев. Anthropic при этом советует сначала пробовать прямые вызовы API и усложнять стек, только когда это оправдано.

Как делать правильно

  1. Зафиксируйте задачу и критерий остановки: что считается решённым, сколько шагов и токенов допустимо, что делать при неудаче.
  2. Составьте карту инструментов по принципу «минимально достаточного набора»: какие действия и источники реально нужны, что останется за человеком.
  3. Опишите каждый инструмент как контракт: имя, описание «когда вызывать», параметры с JSON Schema и описаниями полей, формат результата, ошибки. Проверьте «тестом стажёра»: сможет ли человек выполнить вызов, видя только то, что видит модель.
  4. Определите память: что живёт в контексте диалога, что — во внешнем хранилище, когда история суммаризуется.
  5. Заложите границы полномочий: инструменты только на чтение — по умолчанию; изменяющие состояние — за подтверждением; секреты — вне промпта.
  6. Опишите правила human-in-the-loop и эскалации: условия, маршруты, передаваемый контекст.
  7. Спроектируйте наблюдаемость: трассировка шагов (trace), логи вызовов инструментов, метрики качества и стоимости — до вывода в продуктив.
Как правильно
  • начинайте с простейшей схемы (один вызов, потом workflow) и добавляйте автономию только там, где она измеримо даёт выигрыш;
  • давайте инструментам говорящие имена и описания «когда использовать»; enum-параметры вместо свободного текста там, где множество значений закрыто;
  • возвращайте модели структурированный результат, включая текст ошибки — она учтёт его на следующей итерации;
  • лимиты (шаги, токены, время) задавайте на уровне оркестратора, а не «надежда на промпт».
  • Критерий остановки и лимиты описаны явно и проверяются кодом оркестратора.
  • Каждый инструмент имеет схему, описание и обработку ошибок.
  • Необратимые действия проходят подтверждение человеком.
  • Правила эскалации определены: условия, маршрут, контекст.
  • Шаги агента трассируются: любой прогон можно воспроизвести и разобрать.
  • Стоимость и латентность типового прогона измерены на тестовом наборе.

Пример

Мини-кейс: агент первой линии техподдержки. Инструменты — поиск по базе знаний и создание тикета. Обращение пользователя, на которое в базе нет готового ответа, должно эскалироваться на вторую линию. Схема инструмента поиска (в стиле OpenAI function calling, strict mode):

{
  "type": "function",
  "name": "kb_search",
  "description": "Поиск по базе знаний техподдержки. Вызывай для любого вопроса
    о продукте, ошибках и настройках, прежде чем отвечать или эскалировать.",
  "strict": true,
  "parameters": {
    "type": "object",
    "properties": {
      "query": {
        "type": "string",
        "description": "Поисковый запрос: текст ошибки или вопрос пользователя"
      },
      "product_area": {
        "type": ["string", "null"],
        "enum": ["web", "mobile", "integration", null],
        "description": "Контур продукта, если известен из обращения"
      }
    },
    "required": ["query", "product_area"],
    "additionalProperties": false
  }
}

Что здесь важно: описание отвечает на вопрос «когда вызывать», а не «что делает функция внутри»; optional-поле в strict mode эмулируется объединением с null (все поля обязаны быть в required); additionalProperties: false запрещает лишние ключи. Трассировка типового прогона:

1. user:      "Интеграция отдаёт 401 на /api/v2/orders после обновления"
2. agent  --> kb_search(query="401 /api/v2/orders после обновления",
                        product_area="integration")
3. tool   --> KB-1123: в v2.4 изменена схема авторизации, пример заголовков
4. agent  --> ответ по статье: причина + шаги исправления
5. agent  --> вопрос пользователю: "Не помогло — создать тикет?"   [HITL-точка]
6. user:      "Да, создайте"
7. agent  --> ticket_create(summary="401 /api/v2/orders", priority="normal")
8. tool   --> {"ticket_id": "TS-4821"}
9. agent  --> финальный ответ: решение + номер тикета

Обратите внимание: создание тикета (изменяющее действие) идёт после явного согласия пользователя, а весь путь агента воспроизводится по логу — это база для отладки, аудита и оценки качества.

Антипаттерны

Антипаттерн

Агент там, где хватит workflow. Если шаги процесса известны заранее, свобода модели не даёт ценности — только переменную стоимость и риск зацикливания. Правило: фиксированный путь фиксируйте кодом, агент — для открытых задач.

Антипаттерн

Один агент и тридцать инструментов. Чем больше схем в контексте, тем выше цена каждого запроса и тем чаще модель выбирает не тот инструмент. Дробите домены по агентам, вводите маршрутизацию или подключайте инструменты динамически.

Антипаттерн

Интерфейс инструментов для человека, а не для модели. Названия «получитьДанные2», описания из внутренней документации, свободные текстовые поля вместо enum — модель «не пройдёт тест стажёра». Проектируйте tool calling как API с первого класса.

Антипаттерн

Нет лимитов и критерия остановки. Агент без бюджета шагов способен зациклиться на неудачных вызовах, расходуя токены и время. Лимиты — обязательная часть спецификации, а не «поведение по умолчанию».

Антипаттерн

Полная автономия в необратимых действиях. Удаление данных, платежи, рассылки «по решению модели» — прямой путь к инциденту. Такие действия только через human-in-the-loop или очередь с подтверждением.
