Артефакты аналитика для AI-решений

Спецификация AI-фичи, промпты как требования, архитектурные решения и НФТ для LLM-систем: что меняется в классическом наборе артефактов системного аналитика, когда в системе появляется генеративная модель.

Содержание страницы

Что меняется в аналитике с появлением LLM

Классический набор — требования, сценарии, интеграционные контракты, модели данных — сохраняется. Добавляются артефакты, которых в детерминированных системах не было:

  • промпты и их версии — конфигурация поведения системы, то есть по сути требования, записанные на языке модели;
  • датасеты оценки (golden dataset) — критерий приёмки в виде набора контрольных примеров и порогов по метрикам;
  • бюджеты качества — недетерминированность требует формулировать требования как пороги на распределении ответов, а не как «система отвечает X»;
  • планы деградации — поведение при недоступности модели, при неудачном ретриве, при срабатывании guardrails.
Заметка

Рынок это уже зафиксировал: в вакансиях системного аналитика для AI-продуктов встречается требование приложить к отклику спецификацию AI-фичи — «что должна делать модель, как это описано для разработчиков, как проверялось качество». Спека здесь — портфолио-артефакт в одном документе.

Спецификация AI-фичи

Минимальный рабочий состав спецификации, который закрывает и разработку, и приёмку:

  1. Бизнес-цель и метрика успеха. Какую задачу закрываем и как измерим эффект (доля автоматизированных обращений, снижение времени решения, качество ответов).
  2. Сценарии использования, включая негативные: запрос вне зоны знаний, конфликтные инструкции, неуникальный вопрос, запрос на действие с побочными эффектами.
  3. Границы полномочий. Что агент делает сам, что только предлагает, что передаёт человеку (human-in-the-loop).
  4. Источники данных и инструменты. Базы знаний, API, MCP-серверы; для каждого источника — как учитывается его надёжность и свежесть.
  5. Формат вывода. Структура ответа (JSON Schema при машинной обработке), требование цитат на источники.
  6. Guardrails. Правила отказа, фильтры входа/выхода, обработка инъекций, работа с чувствительными данными.
  7. НФТ. Пороги качества, латентности, стоимости (см. ниже).
  8. Критерии приёмки. Датасет оценки, пороги метрик, объём выборки, регресс-прогон при изменениях промпта или модели.

Каркас такой спецификации в репозитории выглядит так:

docs/
  spec-support-agent.md      # спецификация AI-фичи: сценарии, границы, NFR
  prompts/
    system-v3.md             # текущая версия системного промпта
    CHANGELOG.md             # что менялось и почему, ссылка на замеры
  evals/
    golden-dataset.jsonl     # контрольные вопросы, эталоны, рубрика
    results/2026-11-v3.md    # отчёт прогона: метрики до/после
  adr/
    0001-hybrid-search.md    # архитектурные решения с обоснованием
    0002-escalation-policy.md

Промпты как требования

Промпт — это не «текст для модели», а конфигурация функциональности. Отсюда правила:

Как правильно
  • промпт живёт в репозитории, а не в чьей-то голове или в админке платформы;
  • у промпта есть версия, владелец и changelog с обоснованием изменений;
  • каждое изменение промпта сопровождается прогоном датасета оценки — «изменил — померил — зафиксировал»;
  • требования к поведению формулируются проверяемо: не «отвечает вежливо», а «в 95% случаев оценка судьи по рубрике ≥ 4 из 5».
Антипаттерн

Править промпт в проде «на глазок» без датасета и фиксации версии: поведение системы меняется, но никто не может ни воспроизвести старое, ни объяснить новое.

BRD, HLD и архитектурные решения

Классические документы сохраняют роли, но наполняются AI-спецификой:

АртефактКлассическое содержаниеЧто добавляется для AI
BRD Бизнес-потребность, стейкхолдеры, границы, эффект Метрики качества ответов как бизнес-требование; риски ИИ (галлюцинации, утечки) и допустимые потери
HLD Компоненты, интеграции, потоки данных Выбор подхода: RAG, агент, workflow или комбинация; пайплайн ретрива; guardrails; планы деградации
ADR Зафиксированное решение и его последствия Темы: «гибридный поиск вместо чисто векторного», «эскалация вместо угадывания», «локальная модель против API» — с ценой решения

ADR — самый дешёвый и самый читаемый артефакт: одна страница на решение (контекст → варианты → решение → последствия). Для AI-решений, где выбор часто сводится к трейд-оффам «стоимость / латентность / качество», фиксация обоснования ценнее длинных описаний.

Диаграммы для AI-решений

  • C4, контекст и контейнеры — показать границы системы: где LLM-провайдер, где базы знаний, где инструменты агента, где человек. Отвечает на вопрос «что мы контролируем, а что нет».
  • Sequence-диаграмма агентного сценария — цикл «модель → выбор инструмента → исполнение → результат в контекст → модель», точки эскалации и guardrails. Это главный чертёж для разработчика.
  • Пайплайн ретрива — от запроса до финального top-k: какие фильтры, какие источники, где reranker.
Заметка

Диаграммы — тоже код: PlantUML или Mermaid в репозитории рядом со спекой. Так они не расходятся с текстом и попадают в ревью вместе с изменениями.

НФТ для LLM-систем

ГруппаТребованиеПример формулировки
Качество Пороги метрик на датасете приёмки Faithfulness ≥ 0.9; доля отказов вне зоны знаний ≥ 0.8 корректных
Латентность p95, а не среднее Время до первого токена ≤ 2 с (p95); полный ответ ≤ 15 с (p95)
Стоимость Бюджет на запрос / тикет Средняя стоимость обращения ≤ N руб. при пиковом X
Надёжность Поведение при недоступности Недоступность модели-провайдера → деградация до поиска без генерации
Безопасность Класс входов и выходов Устойчивость к prompt injection по контрольному набору атак; PII не покидает контур
Сопровождаемость Управление версиями Изменение промпта/модели — только через прогон регресс-датасета

Приёмка AI-фичи

  • Golden dataset прогнан, пороги из спеки выдержаны, отчёт приложен.
  • Негативные сценарии проверены: запросы вне зоны знаний, инъекции, конфликтные инструкции.
  • Трейсы типовых сценариев просмотрены: нет зацикливаний, лишних вызовов инструментов.
  • Планы деградации проверены на стенде (недоступность модели, пустой ретрив).
  • Стоимость и латентность замерены на реалистичной нагрузке, укладываются в бюджет.
  • Определён порядок отката: версия промпта/модели, момент переключения, ответственный.
  • Мониторинг в проде настроен до релиза, а не после (см. «Наблюдаемость»).
